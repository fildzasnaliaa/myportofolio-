1. Apa itu debouncing dan mengapa penting pada fitur pencarian yang menggunakan AJAX? Debouncing adalah teknik menunda eksekusi sebuah fungsi sampai pengguna berhenti memicu event tersebut selama jangka waktu tertentu (misalnya 300-500 ms). Setiap kali event terjadi, misalnya penekanan tombol saat mengetik, timer sebelumnya dibatalkan dan timer baru dimulai. Fungsi hanya dijalankan jika timer selesai tanpa ada event baru. Pada pencarian berbasis AJAX, tanpa debouncing setiap ketukan tombol akan langsung mengirim satu request fetch() ke server. Mengetik kata sertifikat saja bisa menghasilkan 10 request berurutan. Hal ini membebani server dan database karena banyak query yang sebenarnya tidak diperlukan, memboroskan bandwidth, dan memperlambat UI terutama pada koneksi yang lambat. Selain itu ada risiko race condition, yaitu response dari request lama bisa tiba setelah response request yang lebih baru, sehingga hasil yang tampil tidak sesuai dengan teks yang sedang ada di kolom pencarian. Daftar yang berkedip dan berubah terus saat pengguna masih mengetik juga membuat pengalaman pengguna kurang baik. Dengan debouncing, request hanya dikirim satu kali setelah pengguna berhenti mengetik, sehingga lebih efisien dan hasilnya lebih konsisten.

2. Apa fungsi await pada fetch() dan apa yang terjadi jika tidak digunakan? 
fetch() bersifat asinkron dan langsung mengembalikan sebuah Promise, bukan data hasil response. await (yang dipakai di dalam fungsi async) menjeda eksekusi fungsi tersebut sampai Promise selesai, baik berhasil maupun gagal, lalu mengembalikan nilai hasilnya. Selama menunggu, thread utama browser tidak diblokir sehingga halaman tetap responsif. Karena itu kita menulis const response = await fetch(url) dan kemudian const data = await response.json(), sebab response.json() juga mengembalikan Promise. Jika await tidak digunakan, variabel response hanya berisi objek Promise yang masih pending, bukan objek Response. Akibatnya response.json(), response.ok, atau response.status tidak dapat dipakai sebagaimana mestinya, misalnya muncul error response.json is not a function atau nilainya undefined. Kode setelahnya juga berjalan lebih dulu sebelum data tiba, sehingga UI bisa merender data kosong atau undefined. Error dari request, misalnya jaringan terputus, tidak akan tertangkap oleh blok try...catch dan muncul sebagai unhandled promise rejection, sehingga kondisi error tidak dapat ditampilkan kepada pengguna. Alternatifnya adalah memakai .then() dan .catch(), tetapi async/await membuat alur kode lebih mudah dibaca karena terlihat seperti kode sinkron.

3. Apa itu serangan XSS dan mengapa data yang ditampilkan lewat AJAX/JavaScript lebih rentan dibanding template Django? 
Cross-Site Scripting (XSS) adalah serangan ketika penyerang berhasil menyisipkan skrip berbahaya, biasanya JavaScript, ke dalam halaman web, lalu skrip tersebut dieksekusi di browser korban. Contohnya, penyerang menyimpan data berisi <img src="x" onerror="alert('XSS!')">. Jika data itu ditampilkan sebagai HTML mentah, browser akan menjalankan skripnya. Dampaknya antara lain pencurian cookie atau sesi, melakukan aksi atas nama korban, mengubah tampilan halaman, atau mengarahkan korban ke situs palsu. Data yang dirender lewat template Django relatif lebih aman karena Django melakukan auto-escaping secara default: karakter seperti <, >, &, ", dan ' diubah menjadi entitas HTML (&lt;, &gt;, dan seterusnya) sehingga dianggap sebagai teks biasa. Sebaliknya, pada AJAX data diambil sebagai JSON dan dirakit sendiri oleh JavaScript, sehingga perlindungan otomatis dari Django tidak berlaku. Jika developer menyisipkan nilai tersebut menggunakan innerHTML atau template literal tanpa escaping, string dari server akan diparsing sebagai HTML sungguhan dan skrip berbahaya bisa berjalan. Karena itu escaping harus dilakukan secara manual. Pada proyek ini diterapkan pertahanan berlapis. Di sisi klien, setiap nilai teks yang disisipkan lewat JavaScript di-escape dengan escapeHtml atau memakai textContent alih-alih innerHTML. Di sisi server, input dibersihkan dengan strip_tags pada method clean_<field> di ModelForm, sehingga tag HTML tidak ikut tersimpan di database.
